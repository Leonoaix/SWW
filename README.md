# SWW — WaterlooWorks 简历匹配

在本机解析你的简历，抓取已登录的 WaterlooWorks Co-op 职位，生成可解释的申请优先级并导出 CSV。

不上传简历、不托管、不需要账号。一个 Python 服务绑定 `127.0.0.1`，一个零运行时依赖的静态页面，数据全在 `.sww/` 下的本机 SQLite 里。

```bash
./scripts/setup-matcher.sh
./scripts/start-matcher.sh
```

打开 **http://127.0.0.1:8765/waterlooworks**。需要 Python 3.10+ 和 Node.js 20+。

使用步骤、评分规则、隐私边界见 **[WATERLOOWORKS.md](WATERLOOWORKS.md)**。

## 流程

```
简历 (PDF / DOCX / MD)
  │
  ├─ 提取正文              documents.py    只做文字抽取，不做解释
  ├─ 分段                  segment.py      教育 / 经历 / 项目 / 技能清单，带字符偏移
  └─ 结构化                profile.py      角色、时长、可用工期、技能→证据
        │
        │  一份简历只拆一次，之后所有职位复用
        ▼
WaterlooWorks 职位
  │
  ├─ 采集                  jobs/crawler.py 你自己登录，串行、自适应限速、可续抓
  │
  │  ── 以下是一条级联：每一层更贵，处理的职位更少 ──
  │
  ├─ 确定性过滤            filters.py     免费          ~700
  │     关闭 / 过期 / 资格 / 关键词 / 重复 / 工期超出可接受范围
  ├─ 混合检索              retrieval.py   免费·本地     ~700
  │     BM25 融合逐块语义最大相似度；有缓存的岗位要求时按要求切块，
  │     否则按句子切块
  ├─ 本地重排              rerank.py      免费·本地      150
  │     cross-encoder 把简历和职位放在一起读，而不是比两个各自算出来的
  │     向量。可选依赖，没装就跳过并说明
  │     └─ 本地模式到此为止，零 API 调用
  ├─ 抽取岗位要求          requirements.py 每职位一次     50
  │     只看职位。按职位内容缓存，改简历不失效，重跑免费
  ├─ 逐条核对简历证据      assess.py       每职位一次     50
  │     引用必须逐字出现在简历里，且落在经历段落而非技能清单
  ├─ 确定性打分            scoring.py      免费
  └─ 近分岗位双向对比      pipeline.py     少量调用
        只调整顺序，不改分数
```

每一层的分工是固定的：**模型只做语义判断，所有能由规则决定的事都由代码决定**——引用是否真实存在、引用落在哪个段落里、工期是否冲突、分数怎么算。

## 设计取舍

**简历先拆分，再匹配。** 以前简历是一整个字符串，任何关于它的问题（那段实习多久？Rust 是用过还是只写在技能栏？能接几个月？）都要在打分时用正则临场回答。现在拆一次、复用到所有职位，`Skills:` 清单和项目经历在数据模型层就是两种东西。

**检索比的是"点"，不是"篇"。** 整篇简历对整篇职位的余弦相似度回答不了任何具体问题，而且长度失配会让它结构性偏小。现在对职位的**每一条要求**去找候选人做过的最接近的**那一件事**，取最大值再按必需/优先加权聚合（late interaction）。这就是为什么一个只写"implement non-blocking consumers"、不提 Python 的岗位也能被找出来。

**BM25 而不是 TF-IDF 余弦。** BM25 有文档长度归一（`b`）和词频饱和（`k1`），正是余弦缺的那两项修正。

**分数用固定校准，不按批次归一。** 除以批次最大值会让最好的岗位永远是 100 分，而且下周多爬到一个更好的岗位会让所有旧分数一起下降。语义分量用固定上下界映射，词频分量用 `x/(x+k)` 压缩。（BM25 的 idf 天然是语料统计量，所以词频分量仍会随语料轻微漂移，量级是零点几分。）

**岗位要求抽取与简历判定分开。** 一个岗位要求什么，跟你的简历没关系。分开之后要求抽取按职位内容缓存，改简历不会作废，只有判定阶段重跑。

**级联，而不是一步到位。** 检索用的双塔向量是各自算出来的，从没见过对方；cross-encoder 把简历和职位放在一起读，信息严格更多，代价是每个职位约 38 ms 而不是一次点积。所以它跑在检索挑出的一百多个上，而不是整块板子上。真正贵的模型层再只看存活下来的，预算花在更对的职位上。

**候选筛选是花钱的唯一闸口。** 上一版对每个合格职位都调用一次模型以避免词面截断——这个顾虑是对的，也正是这里的筛选用语义、再用 cross-encoder 精算的原因。候选数量可以设为 0 做全量评估；结果里永远显示"筛了多少、重排了多少、评了多少、多少没评"，不会把部分结果当成完整排名。

**要求抽取一次，检索受益于之后每一次。** 第一轮检索只能按句子切职位；抽取过的要求进了缓存，从第二轮起检索就按「这个岗位真正要求的每一条」去比，必需条件权重 2、优先 1。

**近分岗位只调顺序。** 上一版对分差 ≤3 的岗位做 ±1 分调整，意味着一个 0–100 的分数取决于它旁边恰好排了谁。现在双向对比的结论只用来交换顺序。

**新近度是一个排序维度，不是证据折扣。** 越近的经历越可能是你想做、也确实还熟练的方向，所以它按结束时间指数衰减（两年半衰，下限 40%）并计入分数。但它衡量的是「支撑这个岗位的是哪段经历」，而不是岗位本身新不新；而且**不会**让久远的证据变成「未体现」——做过就是做过。两个容易踩的坑都踩过了：取 argmax 判断「哪段经历最匹配」时不能用加权后的相似度（否则新经历自动胜出，新近度自我实现），以及新近度必须乘上相关度（否则匹配不上的岗位会靠"空匹配归到新经历"白拿分）。

**限速是速率闸门，不是固定睡眠。** 旧版在每次动作前睡满间隔，于是 2 秒间隔配 2 秒页面加载等于每 4 秒一次请求——延迟被重复计了两遍。现在间隔从**上一次请求**算起，页面加载本身的时间被吸收掉；站点变慢或报 5xx 时间隔自动加宽、恢复很慢，429 直接停。对服务器的请求速率不升反降，但空转没了。

**前端：折叠的东西不构建，筛选不重建。** Top-100 加上每个职位二十多条逐项证据，如果把折叠的 `<details>` 全部提前构建出来就是约 19,000 个 DOM 节点，而上一版在搜索框里每敲一个字符都会把它们全部重建一次（约 34ms，超过 16ms 帧预算）。现在详情在首次展开时才构建，筛选只切换已存在行的 `hidden`：节点数降到 2,300，一次筛选 1.7ms。

## 布局

```
matcher/sww/
  config.py         所有可调参数与上限
  text.py           归一化、分词、引用核对
  store.py          SQLite：职位、模型调用缓存、嵌入缓存
  llm.py            DeepSeek 客户端 + 统一的「缓存→校验→带反馈重试」
  embedding.py      可选的本地 ONNX 嵌入，缺失时降级
  rerank.py         可选的本地 cross-encoder 重排，缺失时跳过
  resume/           documents / segment / skills / profile
  jobs/             crawler / parser / requirements
  match/            filters / lexical / retrieval / assess / scoring / pipeline
  api/              FastAPI 路由、请求模型、本地访问中间件
frontend/src/
  waterlooworks.ts        状态、轮询、事件接线
  matcher/dom.ts          $ / element / 安全外链；一律 textContent
  matcher/wire.ts         线上类型与强制类型转换
  matcher/client.ts       传输层与错误文案
  matcher/results.ts      结果列表：详情懒构建 + 切换可见性筛选
  matcher/resume-panel.ts 简历拆分面板
  style.css               设计令牌与共享控件
  waterlooworks.css       本页样式
```

依赖单向：`api → match → {resume, jobs} → {store, llm, embedding, rerank, text, config}`。前端零运行时依赖，不加载任何外部字体或脚本。

首轮 700 个合格职位的模型调用次数：要求抽取 50 + 逐条判定 50 + 近分对比 ≤12。改简历后重跑只有判定层失效（50 次），原样重跑 0 次。检索和重排全程免费。

## 验证

```bash
.venv/bin/python -m pytest matcher/tests -q
npm --prefix frontend run build && npx --prefix frontend tsc --noEmit
```

271 项测试。爬虫用合成 HTML 在真实 Chromium 上跑分页、弹窗和详情读取；前端集成测试驱动真实构建产物和真实本地 API，模型由脚本假客户端提供，不消耗额度。没装 Chromium 或嵌入模型时相应用例会自行跳过——CI 断言它们确实跑了，因为跳过的测试在汇总里看起来和通过一样。

离线测量排序质量（不需要 API key）：

```bash
PYTHONPATH=matcher .venv/bin/python scripts/evaluate-deepseek.py \
  --fixture matcher/tests/fixtures/semantic_adversarial_cases.json
```

加 `--live` 会额外用真实 API 跑语义链路，走独立的 `.sww/evaluation-cache/`。
